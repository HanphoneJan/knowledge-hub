# 架构总览

> 面向：第一次接手这套代码、想先建立全局图景的人。
> 本文讲**为什么这样切分**，不逐条罗列目录。端点契约见 [`DESIGN-API.md`](./DESIGN-API.md)。

---

## 1. 一次请求里有哪些角色

系统是**三个进程 + 两个存储**，全部跑在一台机器上（单机自部署是明确目标，不是权宜之计）。

```
                      ┌──────────────────────────────────────┐
   浏览器 / 客户端 ───▶│ api（FastAPI） :8010                  │──▶ Qdrant   :6333
                      │  · 检索编排（四条腿）                  │──▶ PostgreSQL :5432
                      │  · 托管前端静态产物                    │
                      │  · MCP /mcp · A2A /a2a                │
                      └───────┬──────────────────────────────┘
                              │ 入队任务 / 查询进度
                              ▼
                      ┌──────────────────────────────────────┐
                      │ worker（**无监听端口**）               │
                      │  · 轮询任务队列 · 摄取 · 清理          │
                      │  · 唯一允许本地加载视觉写入模型的进程   │
                      └──────────────────────────────────────┘

                      ┌──────────────────────────────────────┐
                      │ visual_service :8020                  │
                      │  · 常驻视觉编码模型，启动即预热         │
                      │  · POST /encode（文本）· /encode_image │
                      │  · **不查 Qdrant、不做租户过滤**        │
                      └──────────────────────────────────────┘
```

### 1.1 为什么把视觉编码模型单独拆一个进程

视觉编码模型（`colSmol-500M`）在 CPU 上的实测特性决定了进程边界：

| 指标 | 实测值 |
|---|---|
| 模型加载 | 12.8 ~ 15.0 s · 常驻 RSS **+2.64 GB**（启动即预热，就绪约 13 s） |
| 单图编码 | 常数 **≈15 s/图**（float32）—— 降分辨率 / 降 DPI 完全无效，输出恒 ~862 token |
| 查询文本编码 | 119 ~ 128 ms/条（p95 157 ms） |
| 6 路并发 | 墙钟 0.96 s，消耗 CPU 8.36 s ⇒ **并行度 8.7x**（吃满整机） |

最后一行的 `8.7x` 是拆进程的根本理由：**如果它和 API 同进程**，用户在文档处理期间提问
会把所有核占满、API 长时间无响应。所以定了一条硬约束：

> **API 进程不得加载视觉编码模型。** `pool.get_visual_model()` 在未显式启用它的进程里**主动抛错**，
> 这是有意为之的守卫，不是遗漏。

代价随之而来：API 进程自己就用不上视觉腿。解法不是放宽约束，而是**加第三个进程承担读侧编码**：
API 通过 HTTP 调 `visual_service` 拿到查询向量，**Qdrant 查询与租户过滤仍留在 API 侧**。
这样"API 进程零视觉模型"这条约束一个字都不用改。

### 1.2 那条线为什么刻意断开

`visual_service` 只做「文本/图片 → 向量」。**它不连 Qdrant，也不做任何租户判定。**

租户过滤的构造入口全仓库只有一处（`services/common/auth.py`）。把这个逻辑复制进第三个进程，
就多了一份迟早会漂移的实现 —— 而漂移的方向是**越权看到别人的文档**。
所以视觉腿的查询被拆成三步，只有第一步可能跑在远端：

| 步骤 | 在哪跑 | 理由 |
|---|---|---|
| ① 查询文本 → 多向量编码 | 本进程（若允许）**或**远端 `visual_service` | 只有这步需要重模型 |
| ② 构造租户过滤条件 | **始终在 API 进程** | 过滤唯一入口，不能复制 |
| ③ Qdrant MaxSim 查询 | **始终在 API 进程** | 同上 |

### 1.3 内存预算（单机 15 GB 的取舍）

api ~400 MB（文本模型 100 MB + 两个数据库客户端，峰值 ~600 MB）·
worker ~200 MB（未编码时，加载视觉模型后峰值 **~2.8 GB**）·
`visual_service` **2.71 GB**（启动即预热）· postgres ~200~500 MB · qdrant ~300~800 MB。

worker 与 `visual_service` **各自**要 ~2.65 GB ⇒ 同机峰值约 6 GB。15 GB 够，但小内存机器上必须二选一。
有一个可选的部署形态：把**写侧**（图片编码）也改成走 `visual_service`，worker 便不再自己加载模型
（实测 RSS 降到 ~1 GB），于是同机能跑 **N 个 worker** 而**不**把 2.65 GB 乘以 N。
代价是摄取从此**依赖该服务可用** —— 默认关闭，按机器规格决定。

## 2. 数据流

### 2.1 上传 → 可检索

```
文件 ──▶ ① 上传（同步校验：扩展名白名单 · ≤50MB · 文件头嗅探）
            │  blob 按 sha256 落到 data/blobs/<sha[:2]>/<sha>/original  ← 内容寻址，同一份只存一次
            ▼
         documents 行（PG，status=pending）+ 入队 ingest 任务
            ▼
② worker 领取任务（FOR UPDATE SKIP LOCKED，多 worker 不抢同一行）
            ▼
③ 解析（PDF / Office / 文本 / 图片，见 ingest 派发表）
            ▼
④ 可选切分策略（六选一，默认 recursive；失败一律退回默认并记 note）
            ▼
⑤ 分层校验：格式嗅探 → 解析体检 → 切分体检 ⇒ 报告写 documents.quality
            ▼
⑥ PII 检出（按库决定是否掩码；**只掩码索引侧，不动原件**）
            ▼
⑦ 文本嵌入（512 维）+ BM25 稀疏向量 + 写 PG chunks 行
            ▼
⑧ 扫描页 / 照片页另入队 embed_visual → 多向量写 kb_visual
            ▼
⑨ 任务终态结算：任务是否全部终态 **且** 索引里实际有多少点 ⇒ 才置 ready
```

第 ⑨ 步值得单说：`jobs.status` 与 `documents.status` 是**两份**状态。只看任务状态，
部分失败会被报成 `ready`；只看索引点数，全失败时文档会永远停在 `pending`。
所以判定要同时看两件事，且结算在任务收尾的**事务之外、且不抛异常** ——
不然一次状态写入失败会把 15 秒的模型前向一起回滚。

### 2.2 一次检索

```
客户端
  → auth：API Key → UserContext(readable_kb_ids)      ← 租户过滤唯一来源
  → routing：判查询意图（photo / scan / table / chat / date / general）
             └ 置信度低于 0.35 ⇒ 不路由（等权 + 不过滤）
  → engine：**并发**跑四条腿
       dense   → 编码查询 → Qdrant
       sparse  → 查 PG 词表算 BM25 权重 → Qdrant
       trgm    → Postgres word_similarity
       visual  → ① 编码（本地或远端）② 构造过滤 ③ MaxSim
                 任何一步失败 ⇒ 该腿 skipped + 可操作原因，**不阻塞其它腿**
  → fusion：RRF 融合（只用排名，不用分数）→ 取 top_k × 3 候选进池
  → 软删除二次过滤（PG 已删但索引还在的点必须挡掉）
  → routing.prefer：按意图做**软偏好**过滤（过滤后为空自动退回全部）
  → rerank：仅当该知识库配了精排模型时跑（跨库检索一律不跑）
  → ask：组装证据 → 生成（默认抽取式）→ 引用可核验（块级 + 页面级坐标）
```

细节（RRF 公式、权重、降级行为、坐标）见 [retrieval.md](./retrieval.md)。

**四条腿为什么并发**：实测单腿耗时 dense 56 ms / sparse 153 ms / trgm ~45 ms，串行约 254 ms，
加上查询编码与数据库往返很容易越过 500 ms 的检索段预算；并发后是 `max(...)`。

## 3. 存储分工

### 3.1 Postgres 是真相源，Qdrant 是可重建的派生索引

一条一致性原则贯穿全系统：

> **允许 Qdrant 短暂不一致；绝不允许"Postgres 里有而 Qdrant 里没有"。**

所以删除文档的顺序是：先改 PG（`deleted_at` + `is_current=FALSE`，此刻立即生效）→ 删 blob（仅当引用计数归零）
→ 入队清理任务删索引点 → 30 天后物理清理行。检索时以 PG 的 `is_current` 为准**二次过滤**，
因此即使清理任务还没跑完，被删文档也不会被召回。

有一个**对账任务**在 worker 空闲时定期跑，按腿分别报告「PG 有、这条腿缺」与「这条腿有、PG 缺」，
**只报告不自动修**。设计上有个明确立场：*没有被对账覆盖的检索腿等于不存在的腿* ——
加一条腿就要加一条对账。

### 3.2 为什么是三个 Qdrant 集合而不是一个

Qdrant 的单个集合**不支持"匿名向量 + 命名多向量"混用**，而三种表示形态本来就不同：

| 集合 | 向量形态 | 模型 / 算法 | 承载 |
|---|---|---|---|
| `kb_dense` | dense 512 维 | `bge-small-zh-v1.5` | 所有文本 chunk |
| `kb_sparse` | 稀疏（顶层 `sparse_vectors`） | jieba 分词 + 自实现 BM25 | 同上，词元级精确 |
| `kb_visual` | 命名向量 + multi-vector 128 维 `max_sim` | `colSmol-500M` | 扫描件页 + 照片 |

三个集合的**点 ID 完全一致**：由 `(kb_id, doc_id, chunk_index)` 经 blake2b-64 哈希算出。
用哈希而不是自增序号，是为了能从业务键直接算出点 ID、**不需要先查库** ——
这是"删掉索引再用同一个脚本重建，结果仍然一致"的前提。页级另有一套页级哈希，
用**负**的块序号避开与块级 ID 空间相撞。

三个集合的 payload schema 保持一致（`kb_id` / `doc_id` / `chunk_index` / `source_kind` /
`owner_id` / `workspace_id` / `visibility` / 文本 / 文件名 / 页码 / 坐标），
这样融合时不需要知道一条命中来自哪条腿。

### 3.3 为什么装了 pgvector 却不用它存向量

镜像自带 `pg_trgm`（子串检索必需），所以顺带装了 pgvector；但**向量不放 Postgres**：
一是全局统一了一个嵌入模型 + Qdrant 是既有选型，二是 pgvector **不支持 late-interaction** 多向量，
与视觉腿的能力冲突。Postgres 这边的职责是真相源 + 子串检索 + 任务队列 + 审计。

> 顺带一个实测结论：Postgres 内置全文分词对中文**完全无效**（整行被当成一个 token），
> 且该镜像里没有中文分词扩展。所以 **BM25 留在 Qdrant（jieba），Postgres 只承担字符级子串搜索** ——
> 这也解释了为什么租户过滤要在 Qdrant 和 Postgres 两侧各有一个构造入口。

## 4. 多租户与三档可见性

### 4.1 唯一的租户来源是 API Key

从 API Key 推导出"这个用户可读的知识库集合"。**请求体里不接受 `user_id`，
也不接受任何"我是管理员"之类的字段。** 跨库搜索可以传入一个知识库子集，
但它只用于**求交**：实际范围 = 可读集合 ∩ 请求里的子集，交集只会更小 ——
带着无权限的 kb_id 进来不会越权，只会少结果。

### 4.2 三档可见性必须写成三个独立分支

```python
# ❌ 这段代码有两个独立漏洞
or_(visibility.in_(("workspace", "global")), created_by == me)
#   1. 所有 workspace 库对任何用户可见（少了"我是该工作区成员"这个限定）
#   2. 同工作区成员能看到别人的 private 库（private 混在同一个 IN 里）
```

```python
# ✅ 三个档位各有各的限定条件
global    → 所有用户可见
workspace → visibility == 'workspace' AND workspace_id IN (我的工作区)
private   → created_by == 我
```

**为什么 `IN` 天然是错的**：`IN` 表达的是"任一条件成立即可"，而可见性要表达的是
"不同档位有各自不同的限定条件" —— 语义不匹配。修的时候还有一个很容易犯的二次错误：
保留了裸的 `workspace` 分支，把带成员资格限定的分支**追加成另一条 `or`**，等于没改。
正确的写法是两个条件必须在**同一个 `and_`** 里。

由此推出一条通用纪律：**任何"附加的限定条件"都要先问它是 `or` 的一项还是 `and` 的一项。**
拿不准就写成 `and_(or_(可见性...), 额外限定)`，让结构自己说话。

### 4.3 fail-closed：无权限 ≡ 不存在

无权访问某个知识库时，返回的错误与"这个资源真的不存在"**完全相同**（同一错误码）。
如果分成两种错误码，攻击者就能通过错误码差异探测资源是否存在。

### 4.4 过滤只有一个真相源，但有两个入口

| 函数 | 服务对象 | 用在哪 |
|---|---|---|
| `build_qdrant_filter` | Qdrant | dense / sparse / visual 三条腿 |
| `build_kb_scope_sql` | Postgres | trgm 子串腿 |

两个而不是一个，是因为有一条腿跑在 Postgres 里、拿不到 Qdrant 的过滤字典。
**但两个函数都只读同一份可读集合**，不各自重算可见性 ——
让子串腿自己 join 复刻一遍可见性，就等于开了第二个过滤入口，
而历史上唯一一次真实越权正是"两处各自复刻可见性逻辑"造成的。

这套纪律有测试守着：扫描全仓库 AST，断言除白名单外任何文件不得出现过滤字面量、
每条查 Qdrant 的腿都必须传来自统一入口的过滤条件、检索层不得出现可见性**判定**代码。

## 5. 为什么检索只有一套实现

```
web/ → services/api → services/common → services/retrieval → services/ingest
```

对外有三个入口：REST API、MCP（给 AI 客户端）、A2A（给别的 Agent）。
**三者的检索与问答都调 `services/retrieval/` 的同一个入口**，各自只做协议适配。

理由不是"代码复用"这么抽象：三套检索逻辑一旦各自演化，半年后会出现
**API 搜得到、MCP 搜不到**这类不一致，而且极难排查（两边看起来都"正常"）。
MCP 与 A2A 的差别只在协议形状与权限裁剪：

| 入口 | 协议 | 与内核的关系 |
|---|---|---|
| REST | HTTP + SSE | 直接调 |
| MCP | JSON-RPC over Streamable HTTP（无状态），暴露 4 个工具 | 协议适配层，工具列表按调用者权限动态裁剪 |
| A2A | HTTP 任务式 | 同上，按用途分 Agent |

这条约束同样是**测试钉住的**：运行时只有一棵依赖树、"唯一一份实现"靠扫全仓库 AST 找定义点来保证
（能抓住"有人在第三个地方又写了一份"这种漂移）。顶层目录也有白名单，防止有人把第二套实现目录加回来。

## 6. 几个刻意的边界

| 边界 | 现状 | 为什么这样取舍 |
|---|---|---|
| 文件存储 | 只有本地磁盘 + 内容寻址 blob，**没有对象存储** | 单机自部署是目标形态；blob 按 sha256 分片，同一份文件被多个文档版本引用时只存一次，引用计数归零才物理删 |
| 原件永远保留 | PII 掩码只作用于**索引侧文本**，blob / 预览图 / 下载始终是原文 | 个人知识库的核心用途之一恰恰是"搜我自己的证件号"；掩码若不可逆就会丢数据 |
| 生成层默认抽取式 | 不配置外部 LLM 时答案句子**全部摘自原文**，零外传 | 隐私默认 + 引用 100% 可核验。接外部模型必须显式配置，且分"问答用"与"上下文生成用"两个开关 |
| 精排默认关闭 | 按知识库开启 | cross-encoder 在 CPU 上每对 30~60 ms，20 个候选就是 0.6~1.2 s；而它**只能重排候选、不能扩大召回**，是"提升"不是"解决" |
| 不引入多节点 | 没有分片、没有副本 | 复杂度换不来这个规模上的收益；真要横向扩展，先要解决的是"存储是单机的"这一条 |
