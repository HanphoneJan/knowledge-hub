# 检索与问答

一次检索要回答两个问题：哪些内容相关，以及为什么是它们。Knowledge Hub 用四条召回腿、RRF 融合、查询路由和可选的精排来回答前者，用每条腿的明细、路由结论和引用坐标回答后者。

![检索链路：四条腿并发召回，RRF 按排名融合，软删过滤后按路由偏好重排，再可选精排并组装证据](diagrams/retrieval-flow.svg)

## 四条腿各自擅长什么？

| 腿 | 实现 | 检索方式 | 分数范围 | 强项 |
|---|---|---|---|---|
| `dense` | `services/retrieval/dense.py` | `bge-small-zh-v1.5` 编码 512 维，查 Qdrant 余弦 | 0.2 ~ 0.9 | 语义泛化、同义改写 |
| `sparse` | `sparse.py` + `bm25.py` | jieba 分词 + 自实现 BM25，查稀疏向量 | 0 ~ 40+，无界 | 关键词、人名、术语 |
| `trgm` | `trgm.py` | PostgreSQL `word_similarity()` 字符级三 gram | 0.25 ~ 0.40 | 编号、错误码、文件名片段 |
| `visual` | `visual.py` | colSmol 多向量 late-interaction，MaxSim | 0 ~ 1 | 扫描页、照片 |

单腿实测（同一份评测集）：

| 腿 | R@10 | MRR@10 | 单腿耗时 |
|---|---|---|---|
| `dense` | 0.585 | — | 56 ms |
| `sparse` | **0.756** | **0.681** | 153 ms |
| `trgm` | — | — | 约 45 ms |
| `visual` | photo 1.00 / 扫描页 1.00 / 文本类 0.00 | — | 查询编码 119~128 ms |

`visual` 的 overall 数字没有意义：它只索引扫描页与照片，天然召不回文本类提问。分类别数字才可比，这条纪律适用于所有检索指标。

BM25 有一个容易忽略的分词补丁：`2025-02-14` 会被切成 `2025/02/14`，而“2025年2月14日”被切成 `2025/年/2/月/14/日`，两边没有共同 token。加一个归一化 token `d20250214` 之后，按日期提问的 R@10 从 0.20 升到 1.00。BM25 的 idf 用全局词表与语料统计，因为稀疏向量的下标空间必须全局一致；副作用是一个罕见词在别的库出现过会拉低这边的 idf，只泄漏统计量，不泄漏内容。

`trgm` 的召回条件只能是 `word_similarity` 阈值。`ILIKE '%整句提问%'` 对自然语言提问返回 0 条；整段 `similarity()` 对 8 字 query 与 500 字 chunk 恒在 0.05~0.11；两者 OR 起来仍然漏，因为放宽的是同一个错误判据。实测阈值 0.25 能召回 3 条并含真值 0.400，而 `ILIKE` 与整段 `similarity()` 各返回 0 条。代价是这一腿走全表扫描，用不上 GIN 索引；在这个规模上可以接受——慢能被发现，漏召回不能。

## mode 与腿怎么映射？

| mode | 走哪条腿 | 能搜什么 |
|---|---|---|
| `semantic` | 只走 `dense` | 意思相近 |
| `exact` | 只走 `trgm` | 子串或模糊匹配 |
| `hybrid`（默认） | `dense` + `sparse` + `trgm` | 语义 + 关键词 + 字面 |

`visual` 不在 mode 里。它由 `visual_available()` 决定：本进程允许加载视觉模型，或远端视觉服务可达且模型就绪。这样纯文本查询不会莫名多付一次视觉编码。视觉腿不可用时返回 `skipped`，不是 0 条结果。

默认用 `hybrid`，因为它同时覆盖语义、关键词与字面三种提问方式。`semantic` 与 `exact` 保留下来，一半是给调用方按场景选择，一半是排障：只跑一条腿时，某条腿的召回质量与 `skipped` 原因最容易看清。它们不是“低配版”，而是把单腿行为暴露出来的开关。

三条 DB 腿真正并发。它们各自从会话工厂拿一个 `AsyncSession`，不能共用调用方那个：SQLAlchemy 不允许在同一个 `AsyncSession` 上并发 `execute`，共用会让 `sparse` 与 `trgm` 被记成 `skipped`，`hybrid` 静默降级成 `dense` 单腿，而接口仍然返回 200。代价是一次 `hybrid` 最多占“请求会话 + 3 条腿 = 4 条连接”，连接池按“并发检索数 × 4”估。这里的连接指 API 到 PostgreSQL 的连接池连接，不是浏览器到 API 的 HTTP 连接。

## 为什么用 RRF 而不是加权求和？

四条腿的分数量纲不同，BM25 无界，trgm 只在窄带，dense 有界。要加权就得先归一化，而 min/max 对单次查询的候选集敏感，z-score 会被离群值带跑。RRF 只看排名：

```text
score(d) = Σ_leg  weight_leg / (k + rank_leg(d))        k = 60
```

`k=60` 让 rank 1 与 rank 2 的贡献只差约 0.26%（`1/61` 与 `1/62`），头部的微小优势不会压倒第二条腿的共识。`dense` 与 `sparse` 都排第一的 chunk，应该赢过“只有一条腿排第一、另一条腿排第 30”的 chunk。

两个工程细节：融合 key 必须带命名空间（`text:<id>` / `visual:<id>`），因为文本点与页级点 ID 空间独立，不加前缀会互相抵消；排序要有确定性的 tiebreaker，否则浮点并列时同一个 query 两次请求的顺序会抖动，前端引用角标会在刷新后对调。

默认权重全是 1.0，这是实测结论：等权 RRF 在每个语料类别上都没赢过该类的最佳单腿（chat 1.00→0.90、photo 1.00→0.60、blog 1.00→0.88）。一条固定权重不可能同时是 chat 和 photo 的最优，所以问题不是 k 值，而是该按查询类型换权重。

候选池是 `per_leg = min(100, max(top_k × 3, 30))`，融合池取 `top_k × 2`。池子取两倍是因为路由的偏好只能重排池内已有的结果。融合后先做软删除二次过滤：向量腿可能召回已进回收站的文档，这里用一次 `IN` 查询挡掉，成本与 `top_k` 成正比、与语料规模无关。顺序不能反——先过滤再路由，否则被路由滤掉的命中会被算进“被软删滤掉”的计数。

## 查询路由解决什么问题？

路由用正则识别六类意图，命中后改腿权重、加软偏好：

| 意图 | 腿权重 | 偏好 | 依据 |
|---|---|---|---|
| `photo` | `visual 3.0` | 偏好照片库 | visual 在 photo 类命中最高 |
| `scan` | `visual 2.0` + `sparse 1.2` | 偏好整页与表格块 | 扫描页靠视觉，表单文字靠字面 |
| `table` | `sparse 1.3` + `trgm 1.2` | 偏好表格块 | “哪一栏/怎么填”是字面题 |
| `chat` | `sparse 1.6` | 偏好聊天块与聊天库 | 实测 chat 类 sparse 1.00、dense 0.10 |
| `date` | `sparse 2.5` | 无 | dense 召不回“哪天”；BM25 日期归一化 Hit@1 0.875 |
| `general` | 全 1.0 | 无 | 与引入路由前完全一致 |

`photo → visual 3.0` 是实测出来的。在 60 个照片点 + 60 个文本点、`top_k=10`（融合池上限 20）的对照里：

| visual 权重 | 融合池里的 photo 点数 | top10 里的 photo |
|---|---|---|
| 0.0 / 1.0 | 0/20 | 0/10 |
| 2.0 | 10/20 | 5/10 |
| **3.0** | **20/20** | **10/10** |
| 4.0 / 6.0 | 20/20 | 10/10，与 3.0 等价 |

3.0 是能让 photo 点把融合池装满的最小值，再高没有收益。2026-10-15 重测：8 张照片上文本三腿命中 0.000、visual Hit@1 0.750 / Hit@5 1.000；8 条真实聊天按天查询，sparse Hit@1 0.875、dense 0.250、trgm 0.000；真实 PDF 派生的 4 页扫描件上 visual Hit@1 1.000。

路由有三条原则。**拿不准就不路由**：置信度低于 0.35 返回等权且不过滤；命中多个意图给 0.5，只有日期字面量给 0.6，单一意图给 0.9。**过滤是软偏好**：过滤后为空就退回未过滤，并说明“库里没有照片类型的库”。**只调权重与偏好，不调 k**，k 是排名尺度的定义。

有一个必须知道的机制：执行顺序是先按权重融合到 `top_k × 2`，再做偏好过滤。所以权重决定“哪些结果能进池”，偏好只能重排池内已有的。photo 路由只有在知识库大于 `top_k × 2` 时才有意义；库很小时它与任何权重结果一样，这正是早期对照实验量不出差异的原因。

## 三个可选增强与时间过滤

| 能力 | 做什么 | 默认 | 边界 |
|---|---|---|---|
| 查询改写 | 规则层做规范化与实体词抽取，不外传；可选 LLM 生成 Multi-Query 变体 | 关 | 原始 query 永远排第 0 位；LLM 层需显式配置且功能开关打开 |
| 精排 | cross-encoder 对融合后的候选重新打分 | 按库开启 | 只能重排候选，不能扩大召回；20 个候选约 2.3 s（v2-m3） |
| 证据质量 | 用跨腿共识判 `ok` / `weak` / `none` | 自动 | 只看已有信号；`none` 且生成器不是抽取式时直接拒答，不调 LLM |

精排的开关是 `knowledge_bases.rerank_model`，为 `NULL` 或空串都表示不启用，**不会**回退到全局默认模型。默认模型 `BAAI/bge-reranker-v2-m3`，单对约 114 ms，20 个候选约 2.3 秒；更小的 base 版本在中文公文上只有 2/4 的成对判别正确率，v2-m3 是 4/4，但单对从 53 ms 涨到 114 ms（约 2.2 倍）。跨库检索一律不启用精排，因为不同库可能配了不同模型，排序取决于“哪些库碰巧配了”，那不是用户能预期的行为。

时间过滤是第四个可选能力，参数是 `updated_after` 与 `updated_before`。它在三条 Qdrant 腿的 `must` 里追加一条 `updated_at` 范围条件，在 trgm 腿里追加两个 `Document.updated_at` 比较，与租户条件是并列的 `and`。不传就不改变默认路径；旧点没有 `updated_at` 字段，一旦带时间过滤会被排除，这是重摄取欠账，不是 bug。

查询改写有两层。规则层只做等价改写：全角转半角、折叠空白、抽出编号与长数字；它不会改变词序或删词。LLM 层才会生成不同措辞的变体，检索 query 会离开本机。变体默认最多再产生 2 条（`DEFAULT_MAX_EXTRA = 2`），因为每一个变体都要把三条腿再跑一遍，成本随条数线性上升。原始 query 恒在第 0 位，即使改写模型把“退款”误解成“取消订阅”，原始入口仍在。LLM 失败一律忽略，不影响原检索。

证据质量只看 `FusedHit.legs`：头部最强证据被至少两条腿召回是 `ok`，只来自一条腿是 `weak`，没有命中是 `none`。它不额外查库、不调模型，是纯函数。

## 降级怎么做？

核心纪律是：检索腿是增强项，挂了只降级，绝不 500。

| 腿或能力 | 什么时候 skipped | 文案要求 |
|---|---|---|
| `visual` | 远端不可达、超时、503，或未配置读侧 | 说清怎么修，不能只写“失败” |
| `dense` | 建索引用的模型与当前配置不一致 | 说清索引用哪个模型、现在配的是哪个、怎么修 |
| `rerank` | 库未配置，或模型不可用 | 区分“未配置”与“不可用” |
| 任意腿 | 该腿抛异常 | `skipped` 带原因，其它腿不受影响 |

Embedding 一致性要拦到 `skipped`，因为不同模型的向量空间不通用，混用不是“结果随机”，而是排序基础整个坏了，且不报错。`index_models` 空表表示未知，放行；未知不等于不一致。

“查询侧没跑”与“写入侧没数据”在结果上都表现为这一腿 0 条，所以能力检测不能看集合里有没有点。`GET /health` 的 `available_legs` 汇报这个部署实际能跑哪几条腿；集合为空只说明没数据。

视觉腿的远端调用有硬性防线：超时 2 秒、并发上限 4，排队时间也算在这 2 秒内。跳过的那条腿不参与融合，不能把它的空结果当成“排第 0 名”塞进分母。调试端点里的 `legs[].skipped` 是**字符串或 `null`**，不是布尔值——前端要显示原因，一个空的 `skipped: false` 会让人查错方向。

## 从检索到 SSE 问答

问答在检索之后做四件事：组装证据、生成、校验引用、落库。

- 证据去重：同一 `(doc_id, chunk_index)` 只留一次，否则 `[1]` 与 `[2]` 指向同一段文字。
- 同文档相邻片段按 `chunk_index` 升序排，文档之间按首次出现的位置排。RRF 的相关性序会把同一篇文档的相邻块打散，模型读到的应该是一段连贯的话。
- Parent-Child 库命中子块时，证据正文优先用父块上下文，上限 1200 字符；普通块上限 400 字符。
- 检索只返回 `is_current`，所以同一主题的多个版本不会同时进上下文，这是结构保证。

SSE 帧序固定为 `sources` → `delta*` → `done`。`sources` 在检索一结束就发，前端立刻能画引用卡；`done` 里带 `citations`、`dangling_citations`、`generator`、`session_id`、`history_turns`、`quality` 与每腿的条数、耗时、跳过原因。答案里的 `[n]` 必须对应真实证据，悬空角标要回传而不是静默吞掉。帧字段的完整形状见 [`docs/DESIGN-API.md`](DESIGN-API.md)。

生成层默认抽取式：从证据里挑句子，每条证据最多贡献两句，答案里每一句都能在 `sources` 找到原文。接外部 LLM 需要显式配置，且要 `provider=openai_compat`、`enabled=true`、base_url/model/api_key 齐全。外部生成器失败（401、超时、5xx）时降级回抽取式，并在 `done.degraded` 说明原因，不让整轮问答变成 500。

多轮上下文由两件事组成。生成侧按窗口带最近 4 条消息、最多 4000 字符，按整轮丢弃；检索侧在问题很短且含指代词时，把上一轮问句并进检索 query（上限 24 字符），这一条对抽取式也有效。默认抽取式生成器故意不使用历史，因为它没有语言模型可以条件在对话上；让追问生效的是检索侧的扩展。

## L3 坐标怎么画框？

目标是点开引用就能看到原文那一页、那个框。链路分三段：解析期把 PDF 的 line bbox 除以页面尺寸，归一化到 0~1 存进 `chunks.locations` 与 payload；返回期把 `locations` 随命中带回；渲染期用归一化坐标乘当前页图像素，画矩形。

```jsonc
// 正文块：恰好 1 个框
{"page": 2, "bbox": [0.1360, 0.2301, 0.8638, 0.2585]}
// 表格块：每个非空单元格 1 个框，带 row/col
{"page": 3, "bbox": [0.1055, 0.1954, 0.2446, 0.2403], "row": 2, "col": 0}
```

| 块形态 | `locations` | 前端 |
|---|---|---|
| `text` | 恰好 1 个框 | 直接画矩形 |
| `table` | 每个非空单元格 1 个框，实测最多 40，上限 200 | 按 `row` / `col` 排网格，或用 `table_json` 渲染真表格 |
| `page` | 无 | 只高亮整页，扫描件没有文本层 |
| `chat` | 无真实页码 | 高亮消息序号 |

三个坑。画框要把归一化坐标乘回 PDF point，不是像素，否则框整体下移约半行。形态分派要按 `locations` 的形状，不能按 `kind`：对外引用类型只有 `text` / `page` / `image`，而表格块会以 `kind="text"` 加一堆带 `row` / `col` 的框出现。页图端点要 Bearer，所以前端不能用 `<img src>`，要先 `fetch` 成 blob 再 `createObjectURL`，否则静默 401。

最重要的不变量是：**坐标与被渲染的页面必须来自同一个文件**。PDF 用原件，Office 用转换版；画框用哪个文件由调用方决定，渲染函数不许自己去找原件。定位覆盖率低于 60% 时不给框，而不是给一个错位的框。

## 怎么自己验证？

一次检索的全过程在 `POST /kb/{id}/search/debug`，或普通检索加 `include_debug=true`。返回里有每条腿的召回（含 `skipped` 原因）、RRF 明细、`route` 段（意图、权重、置信度、为什么）、`rerank` 段（是否生效、每个候选的分）。

部署实际能跑哪几条腿看 `GET /health` 的 `available_legs`。差了多少点看一致性对账，按腿分别看。端到端召回质量用 `eval/retrieval_eval.py` 回放；它会写数据，跑之前注意清理，三个 eval 脚本串行跑。

评测指标是 Hit@k、MRR 与 Recall，问题集是人工标注的“问题 → 真值文件 → 真值片段”。看结果要分类别：chat、photo、blog、doc 的强项完全不同，把四类混在一起算 overall R@10 会得到一个不可解释的数。`retrieval_eval.py` 第一次跑就抓到了“hybrid 静默降级成 dense 单腿”，路由 date 权重的方向性错误也是它发现的。改检索前先跑回放，改完再跑一次，别只看“调用返回 200”。
