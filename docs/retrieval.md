# 检索与融合

> 面向：要改检索质量、调权重、或者排查“明明入库了却搜不到”的人。
> 上下文（进程、存储、租户隔离）见 [架构总览](./architecture.md)。

---

## 1. 四条腿

一次 `hybrid` 检索会跑四条腿，然后融合成一个排序。

| 腿 | 实现位置 | 检索方式 | 分数量纲 | 强项 |
|---|---|---|---|---|
| `dense` | `services/retrieval/dense.py` | `bge-small-zh-v1.5` 编码 512 维 → Qdrant 余弦 | 0.2 ~ 0.9（有界） | 语义泛化、同义改写 |
| `sparse` | `sparse.py` + `bm25.py` | 自实现 BM25（jieba 分词）→ Qdrant 稀疏向量 | 0 ~ 40+（**无界**） | 关键词、人名、术语 |
| `trgm` | `trgm.py` | PostgreSQL `word_similarity()` 字符级三 gram | 0.25 ~ 0.40（窄带） | **非词字符串**：编号、错误码、文件名片段 |
| `visual` | `visual.py` | `colSmol-500M` late-interaction 多向量 **MaxSim** | 0 ~ 1 | 扫描页、照片（无文本层的内容） |

单腿实测（同一份评测集）：

| 腿 | R@10 | MRR@10 | 单腿耗时 |
|---|---|---|---|
| `dense` | 0.585 | — | 56 ms |
| `sparse` | **0.756**（四路最强） | **0.681** | 153 ms |
| `trgm` | — | — | ~45 ms |
| `visual` | photo 1.00 / 扫描页 1.00，文本类 0.00 | — | 编码 119~128 ms/条 |

> `visual` 的 overall 数字没有意义：它只索引扫描页与照片（几十个点），天然召不回文本类提问，混在一起算总平均只会得到一个不可解释的数。只有**分类别**数字可比——这条纪律适用于本文所有表格。

### 1.1 `mode` 与腿的映射

| mode | 走哪条路 | 能搜什么 |
|---|---|---|
| `semantic` | 只走 `dense` | 意思相近 |
| `exact` | 只走 `trgm` | 子串 / 模糊匹配（编号、文件名） |
| `hybrid`（默认） | `dense` + `sparse` + `trgm` 三路 RRF | 语义 + 关键词 + 字面 |

`visual` 腿**不在 `mode` 里**：它由“本进程能不能跑视觉查询”决定（本地允许，或远端编码服务可达），这样纯字符查询也不会莫名其妙多花一次视觉编码。

### 1.2 三条值得单说的实现取舍

**BM25 的日期归一化。** `2025-02-14` 被 ASCII 规则切成 `2025/02/14`，而提问里的“2025年2月14日”被切成 `2025/年/2/月/14/日`——两边**没有任何共同 token** 表达“这一天”，而 BM25 无法表达“多词共现”。加一个归一化 token `d20250214` 之后，该类查询的 R@10 从 **0.20 → 1.00**。这是一次典型的“检索质量问题其实出在分词”。

**BM25 的 idf 是全局统计量。** 稀疏向量的下标空间必须全局一致，所以所有知识库共用一个词表与语料统计。副作用：一个罕见词在别的知识库里出现过，这边的 idf 会被拉低——**只泄漏统计量，不泄漏内容**。修法是定期跑重建任务重算，而不是让每个库各算一套。

**trgm 的召回条件只能是 `word_similarity` 阈值。** 试过两种“更快”的写法，都**静默漏召回**：

- `ILIKE '%<整句提问>%'` 与整段 `similarity()` 各返回 0 条；
- 而 `word_similarity(query, chunk) >= 0.25` 返回 3 条且含真值（0.400）。

两个失败版本的共同根因是**它们都要求 query 与整段文本可比**：`ILIKE` 要求 query 是原文的连续子串（自然语言提问从来不是），`similarity()` 按整段长度归一化（500 字块对 8 字 query 恒在 0.05~0.11）。把两者 `OR` 起来**也漏**——放宽的是同一个错误判据，不是换一个判据。

代价是这一腿走全表扫描（`word_similarity` 用不上 GIN 索引），在这个规模上可以接受：**慢能被发现，漏召回不能。**

### 1.3 四条腿真并发：每条 DB 腿用自己的会话

- `dense` / `sparse` / `trgm` 都要做 DB 操作；**不能**共用同一个 `AsyncSession`；
- SQLAlchemy 的 `AsyncSession` **不允许并发 `execute`**，共用会抛 `This session is provisioning a new connection; concurrent operations are not permitted`；
- 后果极其隐蔽：sparse / trgm 被记成 `skipped`，`hybrid` **静默降级成 dense 单腿**，接口仍然 200；
- 现在每条 DB 腿从会话工厂**各拿一个会话**（各自从池里拿一条 PostgreSQL 连接）⇒ 四条腿真正并发；视觉腿不碰 DB，也并发；
- 代价是连接数：一次 `hybrid` 最多占 **请求会话 + 3 = 4 条连接**，池要按 `并发检索数 × 4` 估（池不够时请求排队，不会算错）。

> **"连接"指什么**：API 进程到 PostgreSQL 的**连接池连接**（asyncpg TCP 连接），
> 不是浏览器到 API 的 HTTP 连接。连接池是**进程级**的 —— 每个 uvicorn worker 各有一份，
> 见 `docs/operations.md` §3.1。

这是“检索质量悄悄变差、但不报错”的典型案例。调试面板里看到 `sparse.skipped` 有值，第一反应应该是“会话/连接”，而不是“库里没有数据”。

## 2. RRF 融合

### 2.1 为什么不是加权求和

四条腿的分数量纲互不相同（见第 1 节表格）：BM25 无界且随语料增长，trgm 只在 0.25~0.40 的窄带里，dense 有界。要加权求和就得先归一化，而归一化只有两条路，都不好用：

- **min/max 归一化**对单次查询的候选集敏感（同一段文本在两个 query 下的分数不同）；
- **z-score** 会被那条腿的离群值带跑。

RRF 只看排名，天然规避：

```
score(d) = Σ_leg  weight_leg / (k + rank_leg(d))          k = 60
```

`k = 60` 是 RRF 原论文的取值。它的作用可以从数值上直观看出：rank 1 与 rank 2 的贡献分别是 `1/61` 与 `1/62`，相差约 **0.26%**——也就是说**头部的微小优势不会压倒第二条腿的共识**。这正是想要的性质：`dense` 与 `sparse` 都排第一的那个 chunk，应该赢过“只有一条腿排第一、另一条腿排第 30”的那个。

两条工程细节：

- **key 必须带命名空间**（`text:<id>` / `visual:<id>`）。文本集合与视觉集合的点 ID 空间独立，直接拿点 ID 做融合 key 会让两者互相抵消。
- **排序要有确定性 tiebreaker**。RRF 分是浮点，理论上有并列，不给兜底的话同一个 query 两次请求的顺序会抖动，前端的引用角标会在刷新后对调。

### 2.2 为什么默认权重全是 1.0

这是**实测结论**，不是懒得调：等权 RRF 在**每个语料类别上都没赢过该类的最佳单腿**（chat 1.00→0.90、photo 1.00→0.60、blog 1.00→0.88）。

原因很直白：**一条固定权重不可能同时是 chat 的最优和 photo 的最优。** 所以问题不是“k 值不对”或“权重没调好”，而是“该按查询类型换一套权重”。这就是第 3 节的路由。

`k = 60` 也被刻意保护起来：它是“排名尺度的定义”，不是分类器的旋钮。

### 2.3 候选池与软删除二次过滤

```
per_leg = min(100, max(top_k × 3, 30))     # 每腿候选数，有绝对上限防止负载过大
fused   = rrf(四条腿, limit = top_k × 2)   # 融合池是最终返回量的两倍
  → 软删除过滤 → 路由偏好 → 截到 top_k → 可选精排
```

池子取 `top_k × 2` 而不是 `top_k`，是因为路由的偏好过滤只能**重排池内的东西**（见 3.3 节）。**软删除二次过滤放在融合之后、路由偏好之前**，顺序不能换：

- 索引与数据库允许短暂不一致（删除是异步清理的），所以向量腿可能召回**已进回收站**的文档；
- 这里用一次批量查询挡掉——**绝不允许“数据库已删但索引还能搜到”**，那才是真正的数据泄漏；
- 排在路由偏好前面，否则“被路由滤掉的命中”会被算进“被软删滤掉”的计数里，那个数字的含义就变了。

代价上它只查命中里出现的文档 ID（一次 `IN` 查询），成本与 `top_k` 成正比、与语料规模无关。

## 3. 查询路由与精排

### 3.1 路由做什么

正则匹配 6 类意图（`photo` / `scan` / `table` / `chat` / `date` / `general`），命中后**改腿权重 + 加软偏好**：

| 意图 | 腿权重 | 偏好 | 依据 |
|---|---|---|---|
| `photo` | `visual 3.0` | 偏好照片库 | visual 在 photo 类 R@10 = 1.00 |
| `scan` | `visual 2.0` + `sparse 1.2` | 偏好整页 / 表格类块 | 扫描页靠视觉，表单文字靠字面 |
| `table` | `sparse 1.3` + `trgm 1.2` | 偏好表格类块 | 问“哪一栏/怎么填”是字面匹配题 |
| `chat` | `sparse 1.6` | 偏好聊天类块与聊天库 | 实测 chat 类 `sparse` 1.00 / `dense` 0.10 |
| `date` | `sparse 2.5` | 无 | `dense` 召不回“哪天/什么时候”；BM25 的日期归一化实测 Hit@1 0.875 |
| `general`（兜底） | 全 1.0 | 无 | 与引入路由前**完全一致** |

> 表格 chunk 的文本以一句描述开头（“表格描述：N 行 × M 列；表头：…”），摄取期纯规则生成。`table` 意图偏好表格类块，而描述让“XX 一览表”这类查询在 **dense 腿**也能召回表格——表头是编号 / `值1` 时尤其明显。

`photo → visual 3.0` 这个数字是**实测出来的**。在一组 60 照片点 + 60 文本点、`top_k=10`（融合池上限 20）的对照里：

| `visual` 权重 | 融合池里的 photo 点数 | top10 里的 photo |
|---|---|---|
| 0.0 / 1.0 | 0/20 | 0/10 |
| 2.0 | 10/20 | 5/10 |
| **3.0** | **20/20** | **10/10** |
| 4.0 / 6.0 | 20/20 | 10/10（与 3.0 等价） |

⇒ 3.0 是**能让 photo 点把融合池装满的最小值**，再往上没有收益。

> 2026-10-15 重测：8 张照片上 `dense/sparse/trgm = 0.000`、`visual` Hit@1 = 0.750 / Hit@5 = 1.000；8 条真实聊天按天查询：`sparse` Hit@1 **0.875** / `dense` 0.250 / `trgm` **0.000**；从真实 PDF 派生的 4 页扫描件：`visual` Hit@1 **1.000**、其它三腿 0.000。路由表五行全部有了实测支撑。

### 3.2 三条设计原则

**① 拿不准就不路由。** 置信度低于 **0.35** 时返回等权 + 不过滤，行为与引入路由前完全一致。宁可少优化一点，也不要用一个猜错的意图把结果过滤空——那对用户来说等于“搜索坏了”。置信度分段赋值：命中多个意图 0.5（取更具体的那一个，不是加权求和）、只有日期字面量 0.6、单一意图命中 0.9。

**② 过滤是软偏好，不是硬排除。** 过滤后**为空就退回未过滤**，并在返回的说明里如实写上原因（例如“识别到在找照片，但库里没有照片类型的库，不做过滤”）。硬排除 + 空结果 = 用户看到 0 条。

**③ 路由只调腿权重与偏好，不调 `k`。** `k = 60` 是排名尺度的定义。

**不做什么：** 不做学习出来的路由（要标注数据 + 训练管线）、不改 `mode` 的语义（`semantic`/`exact` 由用户选，不由路由器猜）、不做 LLM 意图识别（那要在编码开销之外再加一次调用）。

### 3.3 一个必须知道的机制：偏好管不到池外

执行顺序：先 `rrf(..., limit = top_k × 2, weights = 路由权重)`，再 `prefer(fused, route)`。

所以**权重决定“哪些结果能进池”，偏好只能重排池内已有的**。推论：`photo` 那条路由在知识库**大于 `top_k × 2` 时才有意义**；库很小的时候，它与任何权重的结果**完全一样**——这正是早期几次对照实验“量不出差异”的原因。

### 3.4 精排（Reranker）

**开关按知识库**：`kb.rerank_model` 非空才跑，空 = 不启用（默认）。默认模型 `BAAI/bge-reranker-v2-m3`（CPU 上单对 ~114 ms），输入是 RRF 融合后的 top_k 候选、每段截断到 1200 字符。**跨库检索一律不启用**；`rerank_model` **只从知识库读，不接受请求参数**——排序是库的属性，同一个问题在不同库里答案不同。

**为什么默认关闭：**

1. 它只能重排候选，**不能扩大召回**——真值不在候选里就救不回来，所以是“提升”不是“解决”；
2. 延迟上，20 个候选就是 0.6~1.2 s，而 `hybrid` 检索本身已是 1 s 量级。

**模型选型也是实测的：** 更小的 `base` 版本在成对判别上只有 2/4，`v2-m3` 是 4/4——而且 `base` 翻车的正是中文公文类语料（它把**标题行**排在**答案段**之上）。代价是单对耗时从 53 ms 涨到 114 ms（2.2×），这也是“默认关闭、按库开启”的另一个理由。

**不可用时如实 `skipped`，不静默降级**：与视觉腿同一套纪律。如果静默降级，用户会以为自己在用精排、实际没有。

### 3.5 三个默认关闭的增强

| 能力 | 做什么 | 默认 | 代价 / 边界 |
|---|---|---|---|
| **查询改写** | 规则层（规范化、抽实体词）**不外传**；再可选 LLM Multi-Query 生成变体 | **关** | 原始 query **永远排第 0 位**一起参与（改错时的兜底）；LLM 层仅在显式配置外部 LLM 且开关打开时生效 |
| **证据质量 / 拒答** | 用 RRF 的**跨腿共识**判 `ok`/`weak`/`none`；`none` 且生成器不是抽取式时**直接拒答、不调 LLM** | 自动 | 只看已有信号，不额外调用；抽取式本来就会在摘不出句子时拒答 |
| **时间过滤** | `updated_after` / `updated_before` 同时收紧三条 Qdrant 腿与 trgm 的 PG 条件 | 不传即关 | ⚠️ 旧点没有 `updated_at` ⇒ 带时间过滤会被排除（重摄取欠账） |

三者都不改变默认路径的排序——这也是它们能“默认关”的前提。

## 4. 降级行为

**核心纪律：检索腿是增强项，挂了只降级，绝不 500。** 检索照常返回其它腿的结果。

| 腿 | 什么情况下 `skipped` | 原因文案要求 |
|---|---|---|
| `visual` | 远端编码服务不可达 / 超时 / 返回 503 | 必须**可操作**（说清怎么修），不能只写“失败” |
| `dense` | **索引与查询的 Embedding 模型不一致**（`index_models` 记的 ≠ 当前配置） | 说清“索引用哪个模型建的、现在配的是哪个、怎么修（改回或重建）” |
| `rerank` | 库未配置精排模型，或模型不可用 | 说明是“未配置”还是“不可用” |
| 任意腿 | 该腿抛异常 | `ok=false` + 原因，其它腿不受影响 |

> **Embedding 一致性为什么要拦到 `skipped`：** 不同模型的向量空间不通用，混用等于在两个空间里算相似度——结果不是“随机”，是**排序基础整个坏了**，而且不报错。所以宁可降级并说清原因，也不静默返回错排序。判据保守：`index_models` **空表 = 未知 = 放行**（还没记录 ≠ 不一致）。

调试端点里的 `legs[].skipped` 是**字符串或 `null`**，不是布尔——因为前端要显示这个原因。一条什么都没有的 `skipped: false` 会让人查错方向。视觉腿的远端调用有硬性防线：**超时 2 s、并发上限 4**，且用单例 HTTP 客户端；失败判定统一走一个出口构造 `skipped` 结果。

### 4.1 两件容易混淆的事

**“查询侧没跑”与“写入侧没数据”在数据面上长得一模一样**——都是“这一腿返回 0 条”。所以判定能力可用性**不能看集合里有没有点**：能力检测只回答“本进程能不能跑”（本地允许，或远端可达且模型就绪）；集合为空只说明“没数据”。

`GET /health` 的 `available_legs` 如实汇报这个部署**实际能跑哪几条腿**（三条文本腿恒在，`visual` 视情况），与“库里有不有照片”是两回事。

**跳过的腿直接不参与融合**——不能把它的空结果当成“排在第 0 名”塞进分母，那会稀释所有结果。好在 RRF 天然支持这一点：一条腿没命中时对总分的贡献是 0，不会拉低别的腿，这正是 RRF 相对加权求和的好处。

## 5. 证据组装与生成

问答的流程是：检索 → 组装证据 → 生成 → 引用校验 → 落库。

- **证据去重**：同一条腿可能命中同一个 chunk，重复会让 `[1]` 和 `[2]` 指向同一段文字。
- **同文档的相邻片段保持原文顺序**：RRF/精排的顺序是“相关性”序，同一篇文档的相邻块可能被打散；把它们按 `chunk_index` 升序排，模型读到的才是连贯的一段。文档之间的相对顺序不变。
- **不会出现版本冲突**：检索只返回 `is_current`，所以“同一主题的多个版本混进上下文”在当前结构下不可能发生。
- **Parent-Child 库**：命中子块时优先用父块上下文（上限 1200 字符），角标仍指子块。
- **默认抽取式**：答案句子从证据里摘出来；接外部 LLM 时才做归纳。
- **引用校验**：答案里的 `[n]` 必须对应真实证据；`dangling_citations` 非空时前端要提示“这条引用失效了”。

SSE 帧序是 `sources → delta* → done`，`sources` 先到就先画引用卡片。详细的帧字段见 [API 契约](./DESIGN-API.md)。

## 6. L3 引用坐标

目标是一句话：**点开引用能直接看到原文那一页、那个框。**

三层链路：

```
① 解析期：pymupdf 拿 line 级 bbox（单位 point）→ 除以页面尺寸 ⇒ 归一化到 0~1
         存 chunks.locations（JSONB）与索引 payload
② 返回期：检索与问答的命中里带 locations
③ 渲染期：归一化坐标 × 页图像素 ⇒ 在前端页图上画矩形
```

**为什么归一化：** 与渲染分辨率（DPI）完全无关。实测往返误差 **0.00e+00 point**。

```jsonc
// 正文块：恰好 1 个框
{"page": 2, "bbox": [0.1360, 0.2301, 0.8638, 0.2585]}
// 表格块：每个非空单元格 1 个框，带 row/col 供前端排网格
{"page": 3, "bbox": [0.1055, 0.1954, 0.2446, 0.2403], "row": 2, "col": 0}
```

| `kind` | 含义 | `locations` | 前端 |
|---|---|---|---|
| `text` | 正文段落 | **恰好 1 个框** | 直接画矩形 |
| `table` | 整张表 | 每非空单元格 1 个框（实测最多 40，**上限 200**） | 按 `row`/`col` 排成网格（或 `table_json` 渲染真表格） |
| `page` | 扫描件 | 无 | **只高亮整页**（没有文本层） |
| `chat` | 聊天 | 无真实页码 | 高亮消息序号 |

### 6.1 坐标往返里的三个坑

**画框必须乘回 point，不是像素。** 绘图 API 要的是 PDF point：

```python
shape.draw_rect(Rect(nx0 * pix.width,  ny0 * pix.height,  ...))  # ❌ 框会整体下移约半行
shape.draw_rect(Rect(nx0 * page.rect.width, ny0 * page.rect.height, ...))  # ✅
```

**形态分派要按 `locations` 的形状，不能按 `kind`。** 对外返回的引用类型只有 `text` / `page` / `image` 三种，而块的形态有四种——所以一个表格块会以 `kind="text"` 加上一堆带 `row`/`col` 的框出现。判据是形状：**有 row/col → 表格网格**；扫描页 → 整页高亮；其余直接画。反过来“从画了几个框反推形态”是错的（14 格的小表会被误判）。

**前端取页图不能用 `<img src>`。** 页图端点要 `Authorization: Bearer`，而 `<img>` 带不了自定义请求头 ⇒ 直接写会**静默 401**，只在控制台看得到。要先 `fetch` 拿 blob 再 `createObjectURL`，并在卸载时释放。

### 6.2 一个比任何实现细节都重要的不变量

> **坐标与被渲染的页面必须来自同一个文件。**

PDF 的坐标按原件排版算；Office 文档没有原生坐标（实测原生块 0/8 有坐标），所以走“转成 PDF → 在那个转换版上算坐标”。用户看到的页图就是那份转换版，文本与坐标**同源**。

推论：**画框用哪个文件由调用方决定**，底图渲染函数不许自己去找原件——否则给 Office 文档画框会直接报错。定位覆盖率低于 60% 时**不给框**，而不是给一个错位的框。

### 6.3 已知边界

多栏排版已做分栏感知（按行水平区间找一条没有任何行跨越的竖直切线，单栏退化为原排序），但表格**跨页续表**仍按页处理、会被截断；页面旋转非 0 时的坐标换算与横排 / 竖排混排均未验证。

## 7. 怎么自己验证

- **看一次检索的全过程**：`POST /kb/{id}/search/debug`，或普通检索加 `include_debug=true`。返回里有每条腿的召回（含 `skipped` 原因）、RRF 融合明细、`route` 段（意图 / 权重 / 置信度 / 为什么）、`rerank` 段（是否生效 / 每条候选的分）。
- **看这个部署实际能跑哪几条腿**：`GET /health` 的 `available_legs`。
- **看某条腿与真相源差了多少点**：一致性对账端点，**按腿分别看**（顶层汇总口径会掩盖“只有一条腿坏了”）——例如视觉腿缺点要重新摄取，而不是重建文本索引。
- **看端到端召回质量**：`eval/` 下的验收脚本。注意它们会清数据，**串行跑**。
