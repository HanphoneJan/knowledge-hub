## 1. 项目解决什么问题

个人或小团队手里通常有三类散落资料：

- **办公文档**：PDF、DOCX、XLSX、PPTX、Markdown；
- **聊天导出**：几万条消息，按天分布；
- **照片 / 扫描件**：没有文本层，OCR 又经常不可靠。

想做到“问一句话就能定位到原文那一页那一句”，有三个真实难点：

| 难点 | 典型失败 | 本项目的回答 |
|---|---|---|
| 资料格式杂、质量脏 | 解析出空文档、乱码、表格错位 | 解析器派发表 + 三层校验 + 失败降级 |
| 问题形态多 | 问语义、问编号、问“哪天”、找照片 | 四路召回 + 查询类型路由 + RRF 融合 |
| 引用不可信 | 只给“相关文档”，点开还要自己找 | L3 坐标：页图 + 命中框，表格按行列画网格 |

更关键的是**它不是一个 demo**：有任务队列、进度、索引对账、备份、恢复演练、契约检查与巡检。这些“不酷”的部分决定了它能不能长期自部署。

## 2. 技术栈知识铺垫

理解后面设计前，先补齐四个技术点，并标注它们在项目中的落点。

### 2.1 PostgreSQL + Qdrant：真相源与派生索引

系统同时用 PostgreSQL 和 Qdrant，但分工不是“关系数据放 PG、向量放 Qdrant”这么简单：

- **PostgreSQL 是唯一真相源**：用户、工作区、知识库、文档元数据、chunk 文本、任务队列、审计；
- **Qdrant 是可重建的派生索引**：`kb_dense`（稠密向量）、`kb_sparse`（BM25 稀疏向量）、`kb_visual`（视觉多向量）。

由此得到一条贯穿全系统的原则：

> **允许 Qdrant 短暂不一致；绝不允许“PostgreSQL 里有而 Qdrant 里没有”。**

删除文档时先改 PG（`deleted_at` + `is_current=FALSE`，立即生效），再异步删索引点；检索时还会用 PG 的 `is_current` 做一次二次过滤。所以即使清理任务没跑完，被删文档也不会被召回。

**为什么装了 pgvector 却不用它存向量？** 镜像自带 `pg_trgm`（子串检索必需），顺带装了 pgvector；但 pgvector **不支持 late-interaction 多向量**，与视觉腿冲突，而且项目已经选定 Qdrant。PG 只承担真相源、子串检索、任务队列与审计。

### 2.2 BM25 与 pg_trgm：两种“字面匹配”

- **BM25** 是词元级算法，擅长人名、术语、关键词。项目用 jieba 分词 + 自实现 BM25，稀疏向量存 Qdrant。
- **pg_trgm** 是字符级三 gram，擅长**非词字符串**：编号、错误码、文件名片段、手机号。

两者不能互相替代。一个实测结论是：**PostgreSQL 内置的 `to_tsvector` 对中文完全无效**（整行被当成一个 token），镜像里也没有中文分词扩展。所以 BM25 留在 Qdrant（jieba），PostgreSQL 只做子串搜索。

### 2.3 Late-interaction 与 MaxSim：视觉腿

扫描件和照片没有文本层，传统 OCR 又贵又不准。项目用 `colSmol-500M` 做**多向量 late-interaction**：一张图编码成一组 token 向量，查询文本也编码成一组，按 **MaxSim** 计算相似度。

代价非常具体：

- 模型常驻 **2.64 GB**；
- 单图编码 **≈15 秒**，且**与分辨率无关**（模型内部固定切 13 个 512×512 图块）；
- 6 路并发墙钟 0.96 秒、消耗 CPU 8.36 秒 ⇒ **并行度 8.7×**，会吃满整机。

所以它必须跑在**独立进程**里，不能和 API 同进程。

### 2.4 RRF：只比排名，不比分数

四路检索的分数量纲完全不同：

| 腿 | 分数 | 实际范围 |
|---|---|---|
| dense | 余弦相似度 | 0.2 ~ 0.9（有界） |
| sparse | BM25 | 0 ~ 40+（无界） |
| trgm | `word_similarity` | 0.25 ~ 0.40（窄带） |
| visual | MaxSim | 0 ~ 1 |

要加权求和就得先归一化，而 min/max 对单次查询的候选集敏感，z-score 会被离群值带跑。**RRF（Reciprocal Rank Fusion）只看排名**：

```
score(d) = Σ_leg  weight_leg / (k + rank_leg(d))        k = 60
```

`k=60` 让 rank 1 与 rank 2 的贡献只差约 0.26%，头部的微小优势不会压倒第二条腿的共识。这正是“多路都认为相关”优于“单路排第一”的数学表达。

## 3. 总体架构：三个进程、两个存储

```
                      ┌──────────────────────────────────────┐
   浏览器 / 客户端 ───▶│ api（FastAPI） :8010                  │──▶ Qdrant   :6333
                      │  · 检索编排（四条腿）                  │──▶ PostgreSQL :5432
                      │  · 托管前端静态产物                    │
                      │  · MCP /mcp · A2A /a2a                │
                      └───────┬──────────────────────────────┘
                              │ 入队任务 / 查询进度
                              ▼
                      ┌──────────────────────────────────────┐
                      │ worker（无监听端口）                   │
                      │  · 轮询任务队列 · 摄取 · 清理          │
                      └──────────────────────────────────────┘

                      ┌──────────────────────────────────────┐
                      │ visual_service :8020                  │
                      │  · 常驻视觉编码模型，启动即预热         │
                      │  · 只做「文本/图片 → 向量」             │
                      │  · 不查 Qdrant、不做租户过滤            │
                      └──────────────────────────────────────┘
```

三个进程的边界不是“微服务拆分”，而是被**资源特性**逼出来的：

| 进程 | 常驻内存 | 为什么单独 |
|---|---|---|
| api | ~400 MB（峰值 ~600 MB） | 轻量、常驻、直接服务用户 |
| worker | ~200 MB（加载视觉模型时峰值 ~2.8 GB） | 摄取是 CPU 密集，不能拖慢 API |
| visual_service | **2.71 GB**（启动即预热，约 13 秒就绪） | 视觉编码会吃满整机 |

`visual_service` 的线**刻意断开**：它只做编码，不连 Qdrant、不做租户判定。因为租户过滤的唯一入口在 `services/common/auth.py`，复制进第三个进程就多了一份迟早会漂移的实现，而漂移的方向是**越权**。视觉腿查询被拆成三步：

1. 查询文本 → 多向量编码（本进程或远端服务）；
2. 构造租户过滤条件（**始终在 API 进程**）；
3. Qdrant MaxSim 查询（**始终在 API 进程**）。

## 4. 摄取链路：从文件到可检索

一次上传到“可检索”经过七个阶段：

```
文件
  → ① 上传（扩展名白名单 · ≤50MB · 文件头嗅探）
  → ② 内容寻址存 blob + documents 行（pending）+ 入队 ingest
  → ③ worker 领取任务（FOR UPDATE SKIP LOCKED）
  → ④ 解析（PDF / Office / 文本 / 图片）
  → ⑤ 切分策略（六选一，默认 recursive）
  → ⑥ 分层校验 + PII 检出/掩码
  → ⑦ 嵌入 + 索引（文本腿 + 视觉腿）
  → ⑧ 终态结算（任务终态 + 索引点数）
```

### 4.1 内容寻址与“扩展名在数据库里”

blob 按 `sha256` 存放：

```
data/blobs/<sha[:2]>/<完整 sha>/original
```

同一份文件传两次只存一份。代价是 **blob 路径没有扩展名**，所以解析器不能从路径猜格式：

```python
# ❌ 每个 blob 都“无扩展名”，解析器一律 UnsupportedFormat
suffix = blob_path(doc.blob_sha).suffix

# ✅ 扩展名 / mime 的真相在 DB 行里
parse_to_chunks(path, file_name=doc.file_name, ...)
```

这个坑会同时炸两处：解析器与页图渲染端点。因此解析入口强制要求传 `file_name`。

### 4.2 解析器派发表

`PARSERS` 是一张 `后缀 → 处理器` 的表，**加一种格式就是加一条记录**。上传白名单由它派生：

```python
SUPPORTED_SUFFIXES, IMAGE_SUFFIXES = _derive_suffix_sets(PARSERS)
```

这样测试可以断言“白名单常量确实等于派发表的结果”，抓住“有人又手写了一份白名单”的漂移。

### 4.3 六种切分策略

切分是**知识库级单选**，默认 `recursive`。没有通吃的一种：

| 策略 | 边界 | 代价 / 前提 |
|---|---|---|
| `fixed` | 定长 + overlap 硬切 | 会切断句子；主要作为评测基线 |
| `recursive` | 标题 > 段落 > 硬切 | 默认值，也是向后兼容契约 |
| `semantic` | 句子向量相似度低于阈值就断开 | 需要句向量编码器；PDF 不执行 |
| `parent_child` | 子块进向量库，父块（章节/整页）进上下文 | 父块文本不进向量库 |
| `late` | 整篇过 Transformer 后按 span 池化 | 受 512 token 上限约束 |
| `contextual` | 每块前置 LLM 生成的上下文 | 需要显式配置外部 LLM |

两个容易踩的顺序约束：

- **策略在解析之后、PII 掩码之前**：策略作用于“内容”，PII 掩码必须作用在最终入库文本上；
- **PII 先检出再掩码**：计数必须记掩码前的，否则报告永远显示“0 处 PII”。

失败一律降级：未知策略、策略抛异常、依赖缺失，都退回 `recursive`，并把原因写进 `documents.quality.strategy_notes`。**不能让“想用新切法”导致摄取失败。**

## 5. 检索链路：四条腿与 RRF

一次 `hybrid` 检索的流程：

```
auth：API Key → UserContext(readable_kb_ids)
  → routing：判查询意图（photo / scan / table / chat / date / general）
  → engine：跑四条腿
       dense   → 编码查询 → Qdrant
       sparse  → 查 PG 词表算 BM25 权重 → Qdrant
       trgm    → PostgreSQL word_similarity
       visual  → 编码 → 构造过滤 → MaxSim
  → fusion：RRF 融合 → 候选池
  → 软删除二次过滤
  → routing.prefer：按意图做软偏好过滤
  → rerank：仅当知识库配置了精排模型
  → ask：组装证据 → 生成 → 引用校验
```

### 5.1 四条腿真并发，但每条 DB 腿用自己的会话

项目文档早期写的是“四条腿并发”，代码里则踩过一个更深的事实：

- `dense` / `sparse` / `trgm` 都要做 DB 操作，如果共用同一个 `AsyncSession`，SQLAlchemy **不允许并发 `execute`**；
- 并发会让 sparse / trgm 被记成 `skipped`，`hybrid` **静默降级成 dense 单腿**，接口仍然返回 200；
- 第一版修法是“加一把锁**串行**”（56 + 153 + 45 ≈ 254 ms，正确，但把并发收益丢了）；
- 现在改成**每条 DB 腿各拿一个会话**（各自的连接）⇒ 四条腿真正并发；视觉腿不碰 DB，也并发。

代价从“延迟”换成了“连接数”：一次 `hybrid` 最多占 **请求会话 + 3 条腿 = 4 条连接**，连接池要按 `并发检索数 × 4` 估；池不够时请求会排队（不会算错，但延迟退化）。

这是一个典型的“看起来正常、实际能力已经退化”的问题，也是后面强调“降级必须如实报告”的原因。

### 5.2 查询路由：拿不准就不路由

路由只做两件事：**改腿权重** + **加软偏好**，不改 `mode`，也不改 RRF 的 `k`。

| 意图 | 腿权重 | 偏好 |
|---|---|---|
| `photo` | `visual 3.0` | 照片库 |
| `scan` | `visual 2.0` + `sparse 1.2` | 整页 / 表格块 |
| `table` | `sparse 1.3` + `trgm 1.2` | 表格块 |
| `chat` | `sparse 1.6` | 聊天块与聊天库 |
| `date` | `sparse 2.5` | 无 |
| `general` | 全 1.0 | 无 |

置信度低于 **0.35** 时返回等权 + 不过滤，行为与引入路由前完全一致。偏好过滤后为空会**自动退回全部**，并如实说明原因。宁可少优化一点，也不要用一个猜错的意图把结果过滤空。

`photo → visual 3.0` 是实测出来的：3.0 是“能让照片点把融合池装满的最小值”，再往上没有收益。

### 5.3 降级：挂了只降级，绝不 500

核心纪律：**检索腿是增强项**。任一条腿不可用，都返回 `skipped` + 可操作原因，其它腿照常返回。

| 腿 | 何时 skipped | 原因要求 |
|---|---|---|
| `visual` | 远端编码服务不可达 / 超时 / 503 | 说清怎么修 |
| `dense` | 索引与查询的 Embedding 模型不一致 | 说清“索引哪个、现在哪个、怎么修” |
| `rerank` | 未配置或模型不可用 | 区分“未配置”与“不可用” |
| 任意腿 | 抛异常 | `ok=false` + 原因 |

`skipped` 是**字符串或 null**，不是布尔——因为前端要显示原因。一条什么都没有的 `skipped: false` 会让人查错方向。

## 6. 多租户：过滤只有一个真相源

### 6.1 唯一的租户来源是 API Key

从 API Key 推导 `UserContext`，其中 `readable_kb_ids` 是“这个用户可读的知识库集合”。**请求体里不接受 `user_id`，也不接受“我是管理员”字段。** 跨库搜索可以传 `kb_ids` 子集，但它只用于**求交**：实际范围 = 可读集合 ∩ 请求子集，只会更小。

### 6.2 三档可见性必须写成三个独立分支

```python
# ❌ 两个独立漏洞
or_(visibility.in_(("workspace", "global")), created_by == me)

# ✅ 三个档位各有各的限定
global    → 所有用户可见
workspace → visibility == 'workspace' AND workspace_id IN (我的工作区)
private   → created_by == 我
```

`IN` 表达的是“任一条件成立即可”，而可见性要表达“不同档位有各自不同的限定条件”，语义不匹配。修复时还有一个常见二次错误：保留了裸的 `workspace` 分支，把带成员资格限定的分支追加成另一个 `or`，等于没改。两个条件必须在**同一个 `and_`** 里。

这条纪律的推论：任何“附加的限定条件”都要先问它是 `or` 的一项还是 `and` 的一项。拿不准就写成 `and_(or_(可见性...), 额外限定)`，让结构自己说话。

### 6.3 无权限 ≡ 不存在

无权访问某个知识库时，返回的错误与“这个资源真的不存在”**完全相同**（`KB_NOT_FOUND` / 403）。如果分成两种错误码，攻击者就能通过差异探测资源是否存在。

过滤条件有两个构造入口，但只读同一份 `readable_kb_ids`：

| 函数 | 服务对象 |
|---|---|
| `build_qdrant_filter` | Qdrant（dense / sparse / visual） |
| `build_kb_scope_sql` | PostgreSQL（trgm 腿） |
| `visible_kb_clause` / `writable_kb_clause` | PG 的 KB 列表与回收站 |

为什么不是一个？因为有一条腿跑在 PostgreSQL 里，拿不到 Qdrant 的过滤字典。但两个函数都**不各自重算可见性**——历史上唯一一次真实越权，正是“两处各自复刻可见性逻辑”造成的。

## 7. 可靠性模式（可迁移）

这一节是整套系统最值得迁移的部分。

### 7.1 真相源与派生索引分离

- PG 写入即生效，Qdrant 异步清理；
- 检索时用 PG 的 `is_current` 二次过滤；
- 对账任务按腿报告“PG 有、这条腿缺”与“这条腿有、PG 缺”，**只报告不自动修**。

设计立场很明确：**没有被对账覆盖的检索腿，等于不存在的腿。** 加一条腿就要加一条对账。

### 7.2 任务终态必须“两件事都算”

`jobs.status` 与 `documents.status` 是两份状态：

- 只看任务状态 → 部分失败会被报成 `ready`；
- 只看索引点数 → 全失败时文档永远停在 `pending`。

所以终态判定要同时看“任务是否全部终态”和“索引里实际有多少点”，并且结算发生在任务收尾的**事务之外、且不抛异常**——否则一次状态写入失败会把 15 秒的模型前向一起回滚。

### 7.3 降级要如实，不能静默

视觉腿不可用、Embedding 模型不一致、精排不可用、Contextual 切分缺 LLM——统一做法是**记 `skipped` / note / `degraded`，让用户看见**。静默降级的代价是用户以为自己在用某个能力，实际没有。

### 7.4 巡检的三态：通过 / 失败 / 跳过

`deploy/monitor.py` 有十四项检查，**“跳过”不算健康**。跳过通常意味着“这项没法验”（例如没有配置巡检 Key），而巡检一半没跑成却报“一切正常”，是监控工具最坏的失败。

退出码 `0` / `1` 要能被 cron 使用，否则“报警”无从谈起。

### 7.5 备份必须恢复过

备份包含 PostgreSQL 与 `data/blobs/`，**不备份 Qdrant**（索引可重建）。但备份目录里有 `manifest.json`，记录各表精确行数、blob 的 sha256、Qdrant 期望点数。恢复演练会建临时库、逐表对账、逐个 blob 校验，然后删掉临时库。

> 没恢复过的备份只是一堆文件。

### 7.6 契约与测试守卫

- 端点契约由 `eval/contract_check.py` 对账路径、方法、**参数面**；
- 关键架构约束用 AST 扫描钉住（租户过滤不得出现在别处、检索实现只有一份、未 await 的协程）；
- 已跟踪文件不得含真实数据，由 denylist 守卫；
- 文档里的路径/命令/端口也有守卫。

这比“写在文档里希望大家遵守”可靠得多。

## 8. 隐私设计：默认零外传

这是项目的第一个卖点，不是事后补的合规声明。

| 设计 | 做法 | 代价 |
|---|---|---|
| 默认抽取式生成 | 答案句子全部摘自原文 | 不做归纳；要归纳需显式接外部 LLM |
| 外部 LLM 显式配置 | 全局单例配置，`enabled` + 用途开关 | 开了就意味着原文会离开本机 |
| PII 掩码按库开关 | **只掩索引侧**，原件/预览/下载仍是原文 | 开了就搜不到自己的号码 |
| 视觉编码只在专用进程 | API 进程恒不加载 colSmol | 多一个进程与 2.65 GB 内存 |
| 外部生成器失败降级 | 401/超时/5xx 退回抽取式并写 `degraded` | 这一轮没有归纳，但不 500 |

PII 检出报告只回答“哪里有、有多少”，**不返回原文片段**——否则报告本身就成了新的泄露面。掩码默认关闭，因为个人知识库的核心用途之一恰恰是“搜我自己的证件号”。

## 9. 性能与容量：实测数字怎么来的

| 指标 | 实测 | 口径 |
|---|---|---|
| dense 单腿 | 56 ms | 同一评测集 |
| sparse 单腿 | 153 ms | 同上，四路里召回最强 |
| trgm 单腿 | ~45 ms | 同上 |
| 检索段 | ~312 ms | 单库 hybrid，含融合 |
| 视觉查询编码 | 119 ~ 128 ms/条 | p95 157 ms |
| 视觉单图编码 | ≈15 s/图 | float32，与分辨率无关 |
| 视觉模型常驻 | 2.64 GB | 启动预热约 13 s |
| 6 路视觉并发 | 墙钟 0.96 s / CPU 8.36 s | 并行度 8.7× |
| 内存峰值 | api ~0.6 GB · worker ~2.8 GB · visual ~2.7 GB | 单机 15 GB |

问答目标：**首 token < 2 秒，检索段 < 500 ms**。生成段靠 SSE 逐字输出掩盖慢速；本机抽取式是毫秒级，接外部 LLM 时可能是 3~8 token/s。

> 单个数字脱离口径没有意义。例如“overall R@10”把四类语料混在一起算，就不能用来做取舍；视觉腿只索引扫描页与照片，混进文本提问算总平均只会得到不可解释的数。

## 10. 刻意的取舍与已知边界

| 边界 | 现状 | 为什么 |
|---|---|---|
| 文件存储 | 只有本地磁盘 + 内容寻址 blob，没有对象存储 | 单机自部署是目标形态；真要上第二台机器时先做只读远端副本 |
| 不做归纳 | 默认抽取式 | 引用 100% 可核验 + 零外传 |
| 精排默认关闭 | 按知识库开启 | 只能重排候选，不能扩大召回；CPU 上 20 个候选要 0.6~1.2 s |
| 不引入多节点 | 没有分片、没有副本 | 复杂度换不来这个规模上的收益 |
| OCR 不做 | 扫描件交给视觉召回 | 不引入 tesseract 这条独立链路 |
| 表格结构化只覆盖 PDF / CSV / XLSX | DOCX / HTML / PPTX 表格仍按纯文本 | 工程量与收益的取舍 |
| 文档没有可信撰写日期 | 文件名是编号 / 修订年份，mtime 是拷贝日期 | 不猜 |
| 无超时保护（前端 Pyodide） | Python 死循环会卡死标签页 | 需要 COOP/COEP + Web Worker，先记为限制 |

## 11. 如果从零实现：演进路线

1. **先做真相源**：PG 表 + 内容寻址 blob + 任务队列，确保“上传后能查到元数据”。
2. **接一条文本腿**：解析 → 切分 → dense 嵌入 → Qdrant，先让“语义相似”可用。
3. **补字面腿**：BM25（jieba）+ trgm。很多“搜不到”其实是字面匹配缺失，不是语义模型不行。
4. **加 RRF**：只比排名，先把多路融合跑通，再考虑权重。
5. **加引用坐标**：解析期存归一化 bbox，前端乘回页图尺寸画框。没有坐标的引用只是装饰。
6. **加租户隔离**：从登录态推导可读集合，过滤条件只在一处构造，无权限与不存在同码。
7. **加视觉腿**：拆独立进程，接远端编码服务，失败降级为 `skipped`。
8. **加运维闭环**：巡检、对账、备份、恢复演练、契约检查。
9. **最后再调质量**：查询路由、精排、改写、拒答、时间过滤——每一项都必须能关掉，默认路径不变。

这条顺序的核心是：**先让系统“可信”，再让它“聪明”。** 引用、隔离、降级、对账，都是“可信”的组成部分。
